Use Cases in Flutter Clean Architecture: Where Should Business Logic Live?

When developers start using Clean Architecture in Flutter, one of the most common questions is: Why do we need a Use Case layer?

At first, it can feel like unnecessary boilerplate. For example, if a repository already has a getUserProfile() method, why create another class called GetUserProfileUseCase that simply calls the repository?

The real value of Use Cases becomes clear when our application contains business rules, validations, and multiple operations that need to work together.

What is a Use Case?

A Use Case represents one meaningful action that the application can perform.

Examples:

Use Case

Repository

Data Source

What is a Use Case?

Each layer has a different responsibility.

BLoC / ViewModel

Responsible for presentation-related concerns:

  • Loading
  • Success
  • Error
  • Refreshing
  • Navigation-related state

Use Case

Responsible for application/business logic:

  • Validation
  • Business rules
  • Decision making
  • Orchestration

Repository

Responsible for data access:

  • API
  • Database
  • Cache
  • Local storage
The important question is not: “Where can I put this code?”Instead, ask: Which layer should own this responsibility?
Real-World Example: Booking a Slot

The user selects a slot and taps Book.

Imagine we have a Flutter appointment-booking application.

The tempting approacheverything inside the BLoC
Future<void> bookSlot(
  BookSlot event,
  Emitter<BookingState> emit,
) async {
  emit(BookingLoading());
  if (!authRepository.isLoggedIn) {
    emit(AuthRequired());
    return;
  }
  final available = await bookingRepository
      .isSlotAvailable(event.slotId);
  if (!available) {
    emit(SlotUnavailable());
    return;
  }
  final count = await bookingRepository
      .getTodayBookingCount();
  if (count >= 3) {
    emit(DailyLimitReached());
    return;
  }
  await bookingRepository.createBooking(
    slotId: event.slotId,
  );
  emit(BookingSuccess());
}

Our requirements are:

  1. User must be logged in.
  2. The selected slot must still be available.
  3. A user cannot make more than 3 bookings per day.
  4. If all validations pass, create the booking.
  5. Show the result to the user.

A developer might put everything inside the BLoC. This code works. But there is a problem.

But there is a problem

The BLoC now knows the business rules.

User must be logged in
        ↓
Slot must be available
        ↓
Maximum 3 bookings
        ↓
Create booking

Now imagine tomorrow the same booking functionality is required from:

If they remain inside the BLoC, we will eventually duplicate them.
Move the Logic into a Use Case

Now the business rules live in one place.

Let’s create:BookSlotUseCase
class BookSlotUseCase {
  BookSlotUseCase({
    required this.authRepository,
    required this.bookingRepository,
  });

  final AuthRepository authRepository;
  final BookingRepository bookingRepository;

  Future<Either<Failure, Booking>> call(
    BookSlotParams params,
  ) async {
    if (!authRepository.isLoggedIn) {
      return Left(AuthFailure());
    }
    final available = await bookingRepository
        .isSlotAvailable(params.slotId);
    if (!available) {
      return Left(SlotUnavailableFailure());
    }
    final count = await bookingRepository
        .getTodayBookingCount();
    if (count >= 3) {
      return Left(DailyLimitFailure());
    }
    return bookingRepository.createBooking(
      slotId: params.slotId,
    );
  }
}
The BLoC becomes much simpler:
final result = await bookSlotUseCase(
  BookSlotParams(
    slotId: event.slotId,
  ),
);
result.fold(
  (failure) => emit(BookingFailure(failure)),
  (booking) => emit(BookingSuccess(booking)),
);
The BLoC doesn’t need to know why the booking failed.It only needs to know:
Success → show success
Failure → show error
So What Exactly Does a Use Case Do?

A Use Case generally answers: What should the application do when the user performs this action?

For example:

Check authentication
        ↓
Check slot availability
        ↓
Check booking limit
        ↓
Create booking
        ↓
Return result
Check authentication
        ↓
Validate file
        ↓
Check storage quota
        ↓
Upload file
        ↓
Save document metadata
        ↓
Return document
Validate cart
        ↓
Check inventory
        ↓
Calculate total
        ↓
Apply discount
        ↓
Create order
        ↓
Clear cart

These are meaningful application actions.

This is one of the most important distinctions

Use Case vs Repository

A Repository answers:

How do I access the data?

bookingRepository.getAvailableSlots();

The repository knows how to retrieve slots.

Repository
    ↓
"How do I get/save the data?"

A Use Case answers:

What should the application do?

bookSlotUseCase();

But this knows the rules required to actually make a booking.

Use Case
    ↓
"What needs to happen?"
This is where Use Cases become particularly valuable

Use Cases Can Coordinate Multiple Repositories

Suppose we are implementing UploadDocumentUseCase. The operation requires:

AuthRepositoryStorageRepositoryDocumentRepository
The Use Case can coordinate them:
class UploadDocumentUseCase {
  final AuthRepository authRepository;
  final StorageRepository storageRepository;
  final DocumentRepository documentRepository;
  Future<Either<Failure, Document>> call(
    UploadDocumentParams params,
  ) async {
    // Authentication
    // Validation
    // Storage quota
    // Upload
    // Save metadata
  }
}

The Use Case is acting as an orchestrator.
This is an important point

But Should Every Repository Method Have a Use Case? No.

You might see code like:
class GetCountriesUseCase {
  Future<List<Country>> call() {
    return repository.getCountries();
  }
}

If the Use Case contains no business rule, transformation, validation, or orchestration, it may not provide meaningful value.

This can become unnecessary boilerplate:
UI
 ↓
BLoC
 ↓
GetCountriesUseCase
 ↓
Repository
 ↓
API

when the Use Case does nothing except forward the call.

Clean Architecture should not mean: “Create a class for everything.”Instead: Create an abstraction when it provides a meaningful separation of responsibility.
Where Should Business Logic Live?

Consider this code.

if (user.isPremium &&
    file.size < user.storageLimit &&
    file.type == DocumentType.pdf) {
  upload();
}

Ask yourself:

UI logic? No. Data-access logic? No. Business/application logic? Yes.

Therefore, it is a strong candidate for the Use Case or domain layer.

The architecture becomes:

A Simple Rule to Remember

When deciding where code belongs, ask three questions.

1. Is it about UI state?

Put it in: BLoC / Cubit / ViewModel
LoadingSuccessErrorSelected tabForm state

2. Is it about business/application behavior?

Consider: Use Case / Domain
Can the user book?Can the user upload?Which discount applies?Can the order be cancelled?

3. Is it about retrieving or storing data?

Put it in: Repository / Data Source
GET /usersPOST /bookingSQLite querySharedPreferencesFirebase
The Main Takeaway

A Use Case is not valuable simply because it exists.

Its value comes from encapsulating application behavior. A good Use Case should answer: What meaningful action is the application performing?

For example:

BookSlotUploadDocumentCreateOrderCancelBookingSubscribeUser

And when the operation involves meaningful business rules, the Use Case becomes a very useful boundary between the presentation layer and the application’s business logic.

The goal of Clean Architecture isn’t to create more files. The goal is to make the codebase easier to:

UnderstandTestChangeReuseMaintain
Validate
      ↓
Decide
      ↓
Coordinate
      ↓
Execute
So when you’re deciding whether to create a Use Case, don’t ask: “Does Clean Architecture require one?”Ask: Is there meaningful application behavior that deserves to be isolated here? That’s the real purpose of the Use Case layer.
